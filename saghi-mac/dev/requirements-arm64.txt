# Saghi arm64 (Apple Silicon) requirements -- the distribution stack,
# resolved from live PyPI data on 2026-08-20 (see packaging/
# build_bundle.py for how it is used).
#
# On Apple Silicon there is no need for the old-stack workarounds that
# Intel Macs need (old transformers, numpy<2, scipy<1.13, a numba shim):
# current torch ships
# real arm64 wheels with MPS support, and current transformers
# (>=5.4.0) natively registers the "cohere_asr" architecture, so
# engine.py's NATIVE load path (_load_native) is what actually runs on
# this stack -- none of the dynamic-module-loading / GenerationMixin
# patch workarounds in the fallback path are needed.
#
# macOS floor: torch is deliberately pinned to 2.11.0, NOT the PyPI
# latest (2.13.0) -- torch dropped macosx_11_0_arm64 wheels starting at
# 2.12.0 and now ships macosx_14_0_arm64 only. 2.11.0 is the newest
# release that still publishes an 11.0-floor arm64 wheel. The actual
# binding floor for this whole stack is macOS 13.0, set by PySide6
# 6.11.2 (its wheel is tagged cp310-abi3-macosx_13_0_universal2) --
# every other package here has a floor at or below 13.0, so pinning
# torch to 2.11.0 keeps the bundle honest about "Apple Silicon M1+,
# macOS 13+", instead of silently
# requiring macOS 14 (Sonoma) because "latest torch" was grabbed
# without checking its wheel tags. Tracking PyPI-latest torch instead
# would raise the real floor to macOS 14 -- that must be a deliberate
# decision, not something shipped silently.
#
# librosa is NOT a Saghi-code dependency (saghi/engine.py deliberately
# avoids it -- see _read_and_prepare's docstring) but it IS a hard,
# unconditional `import librosa` at module load time inside the
# checkpoint's OWN bundled code (model/processing_cohere_asr.py line 6,
# model/modeling_cohere_asr.py line 8) -- confirmed by grep. On arm64, numba publishes real
# prebuilt wheels, so librosa is installed normally here WITH its real
# dependencies (numba, scikit-learn, joblib, decorator, pooch,
# lazy_loader, msgpack) -- no shim, no --no-deps.
